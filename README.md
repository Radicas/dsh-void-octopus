# 虚空八爪鱼（dsh-void-octopus）

一只**透明悬浮**在 DSH Web 界面上的 three.js 虚空八爪鱼。没有方框、没有背景、没有标题栏——它直接漂在对话上方，暗部通过 `mix-blend-mode: screen` 融进页面，只有眼睛、边缘光和触手真正发亮。

它不读你的工作内容，只跟着工作节奏呼吸：空闲时缓慢漂浮，思考时更专注，生成时发亮，跑工具时动作更快、能量更高。

## 当前形态

- 透明 WebGL 层（基准 500px，随深度缩放：最近 500px、最远约 225px）在视口内**自主游走**：原地悬停 4–14 秒（12% 概率是 18–30 秒长休）→ 随机方向、随机速度游一段（1.5–6.5 秒）→ 减速滑行停住 → 再悬停。**没有固定轨迹**，方向与时长都是每次重新掷骰子；同时也是**第三个维度**在慢慢漂移——它会随机地靠近你、也会偶尔退到很远。直接挂在 `document.body` 上（绕开 shell.overlay 的层级与混合上下文），`pointer-events: none`，不挡任何点击。
- 打字/点击时自动淡到 20%，停手 2.6 秒后回到 80%，不抢阅读。
- 窗口、面板、收起按钮全部移除；要关闭它，去 Settings → Plugins 禁用，或：
  ```
  plugin_manager remove_bundle dsh-void-octopus
  ```
- 状态来源只有 `useSessionStatus` 的 `running` 和 `useChat` 的 `runningCalls` / 流式文本长度，不读语义。
- 点击不会脉冲（避免误触界面），鼠标移动会让它轻微转头。
- **远近不再只是缩放**：退远的同时它会**转过去背对你**（距离目标 ≥0.6 就是「决定离开」），并略微上抬、变淡；靠近时再转回来。
- 每隔 1.5–3 分钟它会主动离场一次（转身 → 退远 → 漂一会儿 → 转回来），见 `src/scene/departure.js`。

## 0.9.26 远近=真的离开：背对你 + 不再抖

**现象**（来自实测反馈）：①「由远及近变大缩小，还会有点抖动」；②「缩小的时候没有背面朝我」。

### ① 抖动：变换写得太慢了

| 层 | 0.9.25 及以前 | 后果 |
|---|---|---|
| 层 transform | 每 33 ms 才写一次（≈30 Hz） | canvas 按显示帧渲染，缩放却 30 Hz 跳步 → 抖动 |
| 深度噪声 | 每步 `gauss × 0.02` | 白色噪声直接变成尺寸抖动 |

修法三处：**行为改成每帧步进**（它本来就是 dt 化的，游走统计不变；测试里 `1/30`、`1/120`、`0.05` 三档都验过）、渲染使用的 `depthView` 加一阶低通（τ 0.35 s）、`depthWander` 从 0.02 降到 0.005。真机采样：60 帧里 **59 帧** transform 在变（修复前约一半）。

### ② 缩小却不背对：距离和朝向原本是两条独立通道

0.9.25 里朝向只由「离场编舞」驱动，而远近是另一条随时在重掷的轴，所以它会一边缩一边正脸看你。现在**距离本身就是决定**：

- `depthTarget ≥ 0.6` → 转身背对；`≤ 0.5` → 转回正对（双阈值迟滞，目标停在边界上也不会来回抖）；
- 转身是 1 s 时间常数的指数（≈150°/s 起步，95% 用 3 s），不是瞬移；
- 离场编舞仍然优先：它在近处先转、再退，这一点没变；
- `prefers-reduced-motion` 下整段关闭（不转身，只保留游走）；
- 顺带让「远」有分量：远处同时上抬 22 px、不透明度乘 0.82 —— 远近不再只是尺寸变化。

另外补了一个洞：离场结束回到近处后**先停 4–9 s** 再重掷深度。否则「刚到家」的那一帧可能立刻抽到远带，读作「回来一下又走了」。

### ③ 验证

- `npm test` 新增：远目标 → 背面、近目标 → 正面、迟滞带内不翻面、lift/alpha 随距离、以及「朝向不跳变」（编舞 S 曲线与距离指数转身各有一条理论上限）。
- 真 `client.js` + CDP：`__dshVoidOctopus.depth(0.9)` → `facing 3.14`、`scale 0.516`、`lift 19.4`、`opacity 0.67`；`depth(0.2)` → `facing 0`、`scale 0.88`；控制台无异常。远处背对的实拍见 [design/distance-back.png](design/distance-back.png)。
- 新增调试钩子 `__dshVoidOctopus.depth(0..1)`，方便直接看「近/远」两端的样子。


## 0.9.25 背对你，然后退远

**现象**：这只章鱼在结构上只能正脸示人。0.9.23 给了它游走，0.9.24 给了它远近，但身体的 yaw 一直是「跟随游动 + 鼠标」的混音，并且被 clamp 在 ±0.8 rad —— 超过 90° 才叫「背面」，46° 最多算侧脸。所以无论它游到哪、退多远，你看到的永远是它正对着你。

### ① 两个 yaw 通道，不是一个

| 通道 | 用途 | 约束 |
|---|---|---|
| `sway` | 游动 / 鼠标 / 巡游带来的身体摆动 | 仍然 clamp ±0.8 rad（正是它保证正脸可读） |
| `facing` | 刻意的「转身背对你」 | 可到 π，独立阻尼，不参与 sway 的 clamp |

两者相加后**不再**被 clamp。0.9.24 及以前把 clamp 加在总和上，这才是「背面不可能」的根因。背对时 sway 还会衰减到 30%：身体一边背对你一边扭胯，读起来是「还在展示」，不是「走了」。

### ② 离场是一段有时序的编舞，不是一次赋值

`src/scene/departure.js`：纯函数、可单测，从 REST 出发，每 80–210 s 触发一次（平均约 2.4 分钟）。

| 段 | 时长 | facing | depth | 其它 |
|---|---|---|---|---|
| PREP | 0.5–0.9 s | 0 | 冻结 | 收势，腕先稳住 |
| TURN | 2.0–2.8 s | 0→π | 冻结 | 必须在近处转，退远了看不清转身 |
| RETREAT | 2.6–4.2 s | π | → 0.86–0.97 | 喷水推进一次；层中心上抬 30 px；透明度 → 0.42 |
| FAR | 6–18 s | π | 保持 | `swimAmount → 0`，收拢的腕张开成伞，读作漂着 |
| RETURN | 2.2–3.4 s | π→0 | → 0.18–0.42 | 转回来、拉近、恢复亮度 |

几个刻意的决定：

- **转身期间深度冻结**：否则同一段时间里既「转」又「缩」，两边都看不清。
- **退远不只靠 `scale`**：层中心同时上抬 30 px，否则读作「有人把图片缩小了」，而不是「它走了」。
- **透明度用 CSS 变量复合**：`opacity: calc(.8 * var(--void-alpha, 1))`，`.is-quiet` 与 reduced-motion 同样乘这一项 —— 直接写 inline `opacity` 会把「打字淡到 0.2」覆盖掉。
- **离开期间基础游走被按住**：rest 计时器保底 + 关掉「歇腻了就走」的随机判定，否则它会一边转身一边开始巡游。
- **`prefers-reduced-motion` 整段关闭**：转身 + 退远是大幅运动，正是这类用户明确拒绝的。

### ③ 验证

- `npm test` 新增 [test/departure.test.mjs](test/departure.test.mjs)：相位顺序、转身限速（实测 0.089 rad/step，理论上限 0.098）、转身单调无过冲、耗时 2.0–2.8 s、深度真的进远带、每段离场只喷一次推进、cooldown 间隔、reduced-motion 关闭、中途刷新可续（幂等）、`1/120` 与 `0.05` 两档 dt 不 NaN 且每次都能回得来。

- 角度探针（demo `?facing=`，0/45/90/135/180°，420×420 缓冲）：

### ④ 怎么试 / 怎么改口味

- 不等：控制台 `__dshVoidOctopus.depart()` 立刻来一次；`__dshVoidOctopus.face(180)` 定住角度看背面，`__dshVoidOctopus.release()` 放开。

## 0.9.24 第三个维度：它会靠近你，也会退很远

**现象**：前两个版本里它只是「屏幕平面上的一只 3D 生物」。几何是三维的、朝向也是三维的，但位置只有 x/y，z 恒为 0，所以看起来像贴在玻璃上。

### ① 根因不在生物，在运动接口

| 层 | 0.9.23 及以前 | 后果 |
|---|---|---|
| 运动 | `translate3d(x, y, 0)`，z 恒 0 | 没有远近，只有左右上下 |
| 渲染 | 正交相机 + 全屏 raymarch | 没有「近大远小」，只有大小固定的贴图 |
| 身体内部 | `uOffset.z` 只有 ±0.03 的呼吸漂移 | 那点 z 是姿态，不是位置 |

### ② 方案：深度作为第三个随机维度

行为层多了 `depth`（0 = 最近，1 = 最远）：

- 每 3–12 秒重掷一次目标：70% 落在 0.1–0.5，15% 落在 0.5–0.65，**15% 深退到 0.65–0.95**；
- 以 τ≈2.2 s 阻尼漂过去，叠一点噪声——是「慢慢漂远」，不是「跳大小」；
- 独立于 REST / CRUISE：停下时它也在慢慢远近漂移。

映射是线性的：`scale = 1 - 0.55 × depth`（最近 1.0、最远 0.45）。故意不加曲线——曲线会让远端的小幅变化看不出来，而它大部分时间在近半区。

### ③ 一个关键决定：基准盒按「最近」定，远离靠缩小

CSS 基准盒从 400px 提到 **500px**：「最近」= 1.0 不失真，「最远」= 225px。反过来（400 放大到 500）会让画布被合成器拉伸，**越靠近越糊**——正好在最该看清的时候。

配套两点：

- `transform: translate3d(x, y, 0) scale(s)`：先平移后缩放，元素中心固定在 `(x + 250, y + 250)`，缩放绕中心进行，所以**深度变化不会让图层横向漂移**；行为层的 x/y 语义和边界判定都不用改（视觉盒子始终在基准盒内）。
- 引擎 `resize()` 改用 `clientWidth/clientHeight`（布局尺寸，忽略 CSS transform）而不是 `getBoundingClientRect()`：否则接近时会以当前缩放后的尺寸开缓冲，一放大就自动变糊。

### ④ 兼容与顺手修

- `behavior-v1` 新增 `depth / depthTarget / depthTimer`；**旧存档缺这三个字段时按默认距离恢复**，不换版本、不丢位置。
- 修了一个原有边界 bug：巡航 / 休息结束的那一帧会跳过边界夹取，可能有一帧越界约 0.3 px（随机序列一换就暴露）。现在两个状态切换点都先夹再转状态。

### ⑤ 验证

- `npm test` 新增深度不变量：`depth` 恒在 0..1（900 s）、5 分钟内变化幅度 0.77、远端时间占比 8%、`depthScale` 单调且值域 [0.45, 1]、旧存档迁移、`serialize(restore(x))` 幂等。
- 真浏览器冒烟（缓存 Chromium + CDP）：随机 60 s 窗口里 `scale` 实测 **0.60–0.894**（基准 500 → 视在 300–447 px，恰好等于 500 × scale）；预置存档把深度钉在两端，实测 **0.472 → 视在 236 px**（远）与 **0.965 → 视在 483 px**（近）；`behavior-v1` 里 depth 字段写入正常；控制台无异常。
- 对比图：[design/depth-near.png](design/depth-near.png)（近，483 px）与 [design/depth-far.png](design/depth-far.png)（远，236 px）。

## 0.9.23 随机游走：从「永远在游」改成自主 NPC

**现象**：它一直在游泳，从不停下。调速度、调路径参数都只是让它「游得慢一点」，因为架构上**不存在「停下」这个状态**。

### ① 根因是三层叠加，不是「速度没调好」

| 层 | 证据 | 后果 |
|---|---|---|
| 位置 | `place()` 是 `elapsed` 的纯函数，而 `elapsed` 只增不减 | 位置必然是连续曲线，永不驻留 |
| 接口 | `Math.max(0.15, speed)` | 「静止」这个输入被接口层删掉了 |
| 姿态 | 引擎每 6–12 s 无条件喷水，动量衰减极慢 | 即使外部速度归零，姿态仍被拉成流线型 |

实测（1440×900、默认参数、模拟 120 s）：平均 **62.8 px/s**，p50 65，**最低 22.7 px/s** —— 它从未慢下来过。

### ② 新模型：REST → CRUISE → SETTLE，没有路径

| 状态 | 做什么 | 关键参数 |
|---|---|---|
| REST | 原地悬停，位置只做 ±9 px 的均值回归随机游走 | 4–14 s（u^1.7 右偏），12% 概率 18–30 s 长休 |
| CRUISE | 重掷方向（360°）、速度、时长，位置由速度积分 | 速度 46–66 / 88–115 / 150–195 px/s；时长 1.5–3 / 3–4.5 / 4.5–6.5 s |
| SETTLE | 0.6–1.4 s 内把速度渗到 0，然后回到 REST | 减速 300 px/s² |

**没有目标点，也没有预规划曲线**：每段游走只是「朝这个方向、用这个速度、游这么久」，位置每帧 `pos += dir(heading) * speed * dt`。

随机必须有惯性，否则是布朗噪声而不是生物：步长右偏分布（多数短游、15% 长游）、转向限速 120°/s（180° 掉头要 1.5 s，读作「转身」而不是「瞬移」）、方向带缓慢布朗漂移、边界提前 0.45 s 预测并反射（不会贴边抖动、不会卡角）。

### ③ 引擎只开两个小口子

- **`setAutoJet(false)`**：环境插件自己调度推进（每个巡航段开始时 `pulse()` 一次，正好对应「喷一下 → 滑行」）。引擎原来 6–12 s 的定时喷水会在休息时重新把触手拉成流线型，和「停下时张开」直接冲突。demo / 测试台默认仍开着，行为不变。
- **动作调度解除硬绑定**：忙时（thinking / generating / tool）保留 `look` / `blink` 两种不抢注意力的小动作，大的（coil / wave / stretch / arm / jet）照旧关闭 —— 0.9.3 的承诺不变，但它不再「整个冻住」。

### ④ 停下时真的会张开

调用方不再有 0.15 的下限，`swimAmount` 能到 0，触手回到张开姿态：姿态解算里静止时冠部平均半径 **1.20**，游泳时 **0.88**。0.9.17 修过的 web 裙边只在收拢时露出，所以张开反而把它盖住了，不会以另一种方式回来。

### ⑤ 持久化换成行为状态

旧 key 只存 `elapsed`，因为路径是它的纯函数；现在是状态机，所以存整个状态：

```js
localStorage['dsh-void-octopus:behavior-v1'] = {
  v: 1, rng, mode, timer, x, y, heading, speed, restX, restY, driftX, driftY, ...
}
```

刷新后接着走同一个游走（`rng` 游标也存，所以随机序列可复现）。旧的 `pose-v1` 不再读取，首次升级会从右下角重新入场一次。

### ⑥ 验证

- `npm test` 新增 [test/behavior.test.mjs](test/behavior.test.mjs)：种子可复现、900 s 无 NaN 且不出界（1/30、1/120、0.05 三档 dt）、停留占比 64%、四个象限均覆盖（22 / 27 / 28 / 23%）、边界反弹、恢复确定性、`sin(时钟×状态)` 静态扫描。
- 真实浏览器冒烟（缓存 Chromium + CDP，1440×900，42 s 采样）：

| 指标 | 实测 |
|---|---|
| 首帧（含 SDF 编译） | 19.0 s（无头软渲染；真 GPU 上远低于此，见 0.9.22） |
| 按速度 < 12 px/s 计的停留占比 | **76%** |
| 最长一次连续停留 | **12.2 s** |
| 停留时的位移速度 P50 | 3.9 px/s（即 ±9 px 悬停漂移，不是冻结） |
| 巡航速度 P50 / P95 | 64.8 / 176.0 px/s |
| `localStorage` | `behavior-v1` 写入成功，mode / 位置齐全 |
| 控制台 | 无异常（仅 favicon 404 与一条原有的 shader 编译 warning） |

## 0.9.22 编译耗时：把触手代码从「展开 8 份」改成循环

0.9.21 加环之后仍然「整体卡死」——因为环是 CSS 动画，但 ANGLE 是在 **GPU 进程**里跑 D3D 编译，
GPU 进程一忙，合成器也出不了帧，**环也会跟着冻住**。所以真正要治的是编译耗时本身。

0.9.20 的包围体剔除写成了 8 份展开的 `if` 块（map 里 8 块 × 7 个 capsule，armInfo 里再来 8 块）。
D3D 的编译器（FXC）对满是分支的大段展开代码非常慢。改成循环后，同一份逻辑只剩**一个循环体**：

```glsl
for (int k = 0; k < 8; k++) {
  float boundD = length(q - uArmBound[k].xyz) - uArmBound[k].w;
  if (uCull > 0.5 && boundD >= res.x + 0.05) continue;   // 整条触手跳过
  res = opSmooth(res, capsule(k * 8 + 0, k * 8 + 1), 0.080);
  … 7 段用常量下标 …
}
```

GLSL ES 1.00 允许用循环下标索引 uniform 数组（constant-index-expression），所以
`uArmPts[k * 8 + i]` 合法；管半径也改成 `uRadii[8]` uniform，避免在 shader 里写常量数组。

| 同一台机器、同一无头 ANGLE/D3D11 环境 | 首帧耗时 |
|---|---|
| 0.9.21（8 份展开 + 分支） | 166.8 s |
| 0.9.22（循环） | **9.9 s（快 16.7×）** |

代价是每帧略慢（280 px 2.6 → 3.9 ms，400 px 3.4 → 6.6 ms），仍远在 60 fps 预算内。
这里的选择很明确：**启动时少阻塞一次，比每帧省 3 ms 重要得多**。

顺带确认剔除依然精确：同一冻结姿态下 `uCull` 开/关的 400×400 缓冲 **最大差 1/255，IoU = 1.000**。

## 0.9.21 启动提示：着色器编译时的环形进度

**现象**：打开 Web 界面时会卡顿「一会」，且看不出在等什么。

**根因**：首帧渲染要等 ANGLE 把整只 SDF 翻译成 HLSL 再交给 D3D 编译器，这一步是**同步阻塞**主线程的；
在无头 ANGLE/D3D11 上实测首帧可以阻塞到分钟级（headful 通常只需几秒），期间页面完全没响应。

两件事一起做：

### ① 先画环，再启动引擎

- 宿主层挂载后立刻插入环形加载器（conic-gradient + mask 的细环 + 阶段文字），
  它只做 `transform: rotate` 动画 —— **合成器线程驱动，主线程被着色器编译卡死时它照样转**。
- 引擎启动延后两帧（`rAF → rAF`），保证环已经上屏，之后才开始创建 WebGL 上下文。
- 阶段文字：`初始化 WebGL → 编译着色器 → 就绪`，跟随 `onStage` 回调更新；就绪后环淡出并移除。
- 加载器跟随 `prefers-reduced-motion` 降级为呼吸式明暗。

### ② 编译改为异步，不再堵住主线程

`renderer.compileAsync()`（`KHR_parallel_shader_compile`）先把程序提交给 GPU 进程，
主线程继续跑；程序就绪后再启动渲染循环并上报 `ready`。

需要特别注意的坑：**`compileAsync` 的 Promise 可能长期不 resolve**（本机无头 ANGLE 上实测就卡在
pending，而 `gl.finish()` 又不等 GPU）。所以加了 8 秒兜底：到点直接渲染首帧（此时才阻塞），
环仍在转 —— 生物绝不会因为一个 Promise 永远不出现。同理，宿主侧还有 30 秒的安全超时，
避免 WebGL 上下文丢失时环永远挂着。

引擎新增 `onStage` 回调（`context` / `compile` / `ready`），`debug.getStats()` 里也能读到
`firstFrameMs`，方便以后定位「首帧为什么慢」。

## 0.9.20 清晰度：把像素预算从"省成本"换成"买分辨率"

**现象**：整只生物发糊，眼睛和触手吸盘都看不清。

**实测根因不是材质，是分辨率。** 400 CSS px 的层，自适应分辨率长期停在 **0.7**（缓冲 280 px），
再被合成器放大到 400 px；若系统缩放 125%/150%，还要再放大一次，等于两次插值。它之所以停在
0.7，是因为 400 px 渲染要 **27.9 ms/帧**（Intel UHD，`gl.readPixels` 强制同步实测），
60 fps 的预算是 16.7 ms。降分辨率是当时唯一能同时保住帧率的做法。

所以先降成本，再把省下的钱全换成像素。

### ① 包围体两级剔除（成本降 6–8 倍，且不改变解）

每个采样点原本无条件算 56 个 capsule。现在 CPU 每帧为每条触手算一个**保守包围球**（8 个控制点
的质心 + 到最远点的距离 + 管半径），躯干再加一个：

| 层级 | 条件 | 行为 |
|---|---|---|
| 远场 | 9 个包围球全部 ≥ 0.3 | 只返回 `min(球距)`，**一次 distance 都不算**（球距是严格下界，可安全步进） |
| 近场 | 有球 < 0.3 | 算精确 SDF，但**跳过**那些球距 ≥ 当前精确距离 + 0.05 的触手 |

两条路径都只用**下界**：球距永远小于等于真实距离，所以步进既不会穿过表面，也不会把包围球当成
表面（v0.9.13 的假面事故）。跳过判定额外留 0.05 的余量（大于 smin 最大外扩 k/2 = 0.04），
所以身体与触手根部的融合带不受影响。

> 开发中先试过更激进的写法：每个球外一律用球距参与 min。数学上合法，但**收敛会退化成爬行** ——
> 球是长条触手的松包围，采样点会沿着"球壳"以 0.0015/步挪动，30 步上限内走不到表面，于是
> 触手缺一块。两级结构正是为了避开这个"合法但不可用"的陷阱。

### ② 旋转合成移到 CPU

`map()` 里原本每个采样点做 3 个 mat3 连乘（`rotZ·rotX·rotY`）。改为每帧在 CPU 合成一个
`uInvRot`，shader 里只剩一次 `mat3 × vec3`，几何完全等价。

### ③ 命中阈值按像素换算

固定 `0.0015` 在 280 px 下只有 0.15 px，是纯粹的浪费。改成 `4.1 / 分辨率 × 0.32`
（夹在 0.0016–0.005），亚像素精度不变，步数明显减少。

### ④ 分辨率策略重写（DPR 感知）

| 参数 | 旧 | 新 |
|---|---|---|
| 比例含义 | CSS 的 0.45–0.85 | **设备像素**，0.9–(DPR×1.15，上限 1.6) |
| 起始 | 0.70 | 1.00 |
| 最低 | 0.45（180 px） | 0.90（360 px） |

顺手修掉一个隐患：demo 模式原来 `setPixelRatio` 与 `renderScale` 相乘，实际比例被放大两次；
现在统一由 `renderScale` 表达，两种模式一致。

### ⑤ 细节不再被采样成噪点

- **吸盘**从 72 周期/触手降到 26：原来每条吸盘条纹不到 2 px，采样后就是一层脏噪点；
- **bloom** 半径 0.45 → 0.30、强度 0.24 → 0.20：光晕不再把整圈轮廓糊掉，眼睛的高光仍是唯一
  真正 bloom 的部分。

### 实测（Intel UHD，400 px 层）

| | 旧 | 新 |
|---|---|---|
| 280×280 | 16.0 ms | **2.6 ms** |
| 400×400 | 27.9 ms | **3.4 ms** |
| 500×500 | — | 5.9 ms |

同分辨率下 shader 成本降 **6.2×**，于是 400 px 原生分辨率只花 3.4 ms，60 fps 预算还剩 80%。
自适应现在会稳定在 400–460 px，而不是 280 px。

### 回归验证

- **剔除正确性**：同一冻结姿态下，`uCull` 开/关两张 400×400 缓冲逐像素比对，
  **最大差 2/255，IoU = 1.000** —— 剔除没有改变任何一条光线。
- `npm test` / `npm run selfcheck` 通过。
- 验证台：`test/perf.html`（400 px ambient 层）+ `test/perf-entry.js`，引擎暴露
  `debug.setRenderScale / setCulling / pause / capture / renderFrames`，用于固定比例、
  冻结姿态、A/B 剔除和强制同步计时（`gl.finish()` 在无头 Chromium 里不等 GPU，
  必须用 1 px 的 `readPixels` 才能测到真实耗时）。

## 0.9.17 游泳时的"裙子"：web 蹼膜没跟着触手收

**现象**：一游起来，身体下方多出一圈连续的膜，像穿了条裙子，8 条触手之间的边界也糊成一片。

**两个原因叠在一起。**

### ① web 是固定半径，游泳时被"露"了出来

shader 里身体下方有一圈裙边：

```glsl
float webR = mix(0.5, 0.78, webT);   // 半径固定 0.5~0.78
```

**静止**时八条触手张开到半径 1.65，把这一圈完全挡住，所以看不见。
**游泳**时触手收拢到 1.16 以内，web 就露了出来，独立成一圈裙摆。

`uSwimAmount` 这个 uniform 在 shader 里**声明了却从来没被使用过**——它本来就是为这件事准备的。
现在让 web 跟触手一起收缩：

```glsl
float webR = mix(0.5, 0.78, webT) * (1.0 - uSwimAmount * 0.42);   // 最多缩到 0.58 倍
```

CPU 侧 `uSwimAmount` 现在传 `effort`（含动量），和姿态用的是同一个量，不会脱节。

### ② 触手之间的平滑并集半径太大

```glsl
opSmooth(res, vec2(sdCapsule(...), 2.0), 0.08)   // 全部 56 段都 0.08
```

`0.08` 的融合半径意味着相距小于 0.08 的表面会被融成一片。触手收拢后相邻间隙只剩约 0.09，
**刚好落进融合范围**，8 条独立的触手就糊成了一张连续的面。

现在分段设置：

| 段 | 融合半径 | 理由 |
|---|---|---|
| 第 0 段（根部） | 0.080 | 保留，让触手从身体里"长出来"，不留接缝 |
| 第 1–6 段 | **0.045** | 触手之间不再互相粘连，8 条边界清晰 |

同时把游泳收拢从 `1 - effort*0.38` 收到 `1 - effort*0.30`（收得浅一点，间距留出来）。

> 判据：`opSmooth` 的 k 必须**小于相邻触手的实际间隙**。触手半径约 0.175，8 条在半径 0.63
> 的圆周上时间距约 0.49，减去两个半径剩 0.14；k 取 0.045 是安全值，0.08 就会粘连。

## 0.9.16 修掉 wave 引入的抖动 + 把"原地划水"改成真的在游

### ① 抖动回归：`wavePhase * waveAmount` 又是 `t·f(t)`

0.9.15 加 crown-ripple 时写了：

```js
const phase = k * 1.7 + wavePhase * waveAmount   // ← 同一个错误
```

`wavePhase` 是累积时钟（`+= dt*1.5`），`waveAmount` 是变量。`waveAmount` 一动，相位就被时钟
放大 —— 和 0.9.11 修掉的那个是完全同一种结构。表现也一样：**刚启动不明显，游一会儿才开始抖**。

修法是把**偏移量**积分，而不是把时钟乘以幅度：

```js
waveOffset += dt * 1.5 * waveAmount        // 幅度只改变变化速率
const phase = k * 1.7 + waveOffset         // 相位本身连续
```

> 规律：凡是 `sin(相位)`，相位里**只能出现累加量**，绝不能出现「时钟 × 某个状态」。
> 幅度要影响波形，就让它乘在**外面**，或者乘在**相位的增量**上。

已重新审计全部 20 处 `sin/cos`：其余都是固定频率，或「累积相位 + 常量偏移」，安全。

### ② "原地划水"：两个原因叠加

**a. 位置推进用错了时间基准。** 主循环按显示刷新率跑，但每 33 ms 才 `place()` 一次，
而 `elapsed` 每次只加**单帧 dt（16.7 ms）**：

```js
const dt = (now - last) / 1000                    // 16.7 ms
if (now - lastMove >= 33) {                        // 实际过了 33 ms
  elapsed += dt * speed * (0.8 + jet * 1.6)        // ← 只加了 16.7 ms
```

**layers 的真实速度只有一半。** 改成用实际间隔：

```js
const step = Math.min(0.1, (now - lastMove) / 1000)
elapsed += step * speed * (5.5 + jet * 3.5)
```

**b. 速率本身太低。** 叠加起来实测：

| | 平均速度 | 游完一个身长（400 px） |
|---|---|---|
| 0.9.15 | **22.7 px/s** | 17.6 s |
| 0.9.16 | **96.1 px/s** | **4.2 s** |

同时把 `swimAmount` 的归一化从 `/55` 提到 `/140`：速度真的上来以后，旧的除数会让它一直顶在
1.0，身体永远保持流线姿态、再也不会松开。现在范围是 0.15–1.00，快慢都有姿态变化。

## 0.9.15 虚空游泳：惯性主导 + 三个新动作

**虚空不是水。** 之前所有运动参数都是按水调的——有阻力、有重力、姿态快速收拢。虚空的物理
应该是反的：

| | 水 | 虚空（现在） |
|---|---|---|
| 推进后 | 撞上阻力，迅速减速 | **一次喷水滑行数秒** |
| 触手 | 被水流推向后，随即收拢 | 被**惯性**留在原地，缓慢拖成流线，再慢慢松开 |
| 姿态 | 有"下"（重力） | **没有固定上下**，三轴漫游 |
| 动作 | 受介质约束 | 可以整体收缩、可以让波动绕冠传播 |

### ① 惯性动量 `momentum`

喷水不再只是一次姿态脉冲，它给身体**留下动量**，且衰减极慢（τ≈2.4 s，水大约是 0.1 s）：

```js
momentum = Math.min(1.6, momentum + 1.0)   // 喷水时
momentum *= Math.exp(-0.42 * dt)           // 每帧极慢衰减
const effort = Math.max(swimAmount, momentum * 0.72)
```

`effort` 替代原来的 `swimAmount` 驱动整个流线姿态。实测一次喷水后：0.715 → 1 s 0.473 →
3 s 0.203 → 6 s 0.058。**这就是"滑行"和"衰减"的区别。**

### ② 两个只有虚空才成立的动作

- **coil**：八条触手整体向心收拢（半径 ×0.56）再慢慢张开。水里有浮力会把你顶出来，真空里
  必须靠自己慢慢放。释放 λ=1.9，比手臂弹簧慢一档。
- **wave**：一道波**绕冠传播**。实现是把 `wavePhase` 累加进每条臂的相位差
  （`phase = k*1.7 + wavePhase*waveAmount`），所以相位差自己在流动。仍然不是 `t·f(t)`，
  相位连续。

动作分配重排为 7 种（look / arm / stretch / jet / blink / **coil** / **wave**）。

### ③ 三轴漫游

身体偏移原来只有 y（`uOffset.set(0, breathLift, 0)`），那是重力世界的东西。现在：

```js
uOffset = (
  sin(t*0.19)*0.04 + sin(t*0.071+1.3)*0.022,
  breathLift,
  cos(t*0.23)*0.034 + cos(t*0.089+2.1)*0.018,
)
```

三个**互质**速率，位置永不精确重复。**"下"不再特殊**——它横向漂得和纵向一样随意。

每个触手控制点还加了一层自己的缓慢漂移（频率常量 0.31，相位连续），所以触手是"各自漫游"，
不是"围绕静止姿态摆动"。

### ④ 触手更飘

阻尼比 `0.95-0.08·pt` → `0.93-0.082·pt`，尖端 ζ 从 0.39 降到 **0.356**，过冲 26.4% → **30.2%**。
衰减更慢 = 漂得更久。

## 0.9.14 回退 0.9.13 的 shader 优化（SDF 包围球余量算错 → 头部假面）

0.9.13 为了提帧率动了三处 shader，其中**包围球早退是错的**，直接把头搞坏：

```glsl
float dHead = length(q - vec3(0.0, 0.7, 0.0)) - 1.15;   // ← 1.15 不够
float dArms = length(q - vec3(0.0, -0.8, 0.0)) - 2.4;
if (dOuter > 0.0) return vec2(dOuter, 0.0);            // 空区域被判成表面
```

mantle 椭球（中心 (0,0.98,0)，半轴 0.52/0.6/0.46）最远点 (0.53, 1.59, 0.47) 到
head 球心 (0,0.7,0) 的距离是 **1.14**，`breath` 一波动（×1.02）就是 **1.16 > 1.15**。
球外的那片**空区域**于是收到一个很小的正距离，raymarch 把它当成表面逼近并判定命中，
头部边缘出现假面/破面。

**SDF 的界必须严格保守**，差 0.01 就会长出并不存在的表面。这跟"大概差不多"的调参不一样：
包围体一旦不包含全部几何，得到的就不是近似解，而是错的解。

同时 `MAX_STEPS` 30 → 24 也让眼窝 / siphon 这类高曲率细节收敛不足。

### 保留

- 去掉 24 fps 上限（这条与几何无关，是纯粹的帧调度问题）
- 自适应分辨率（只改 render target 尺寸，不改几何）

> 教训：**优化只该在不改变"解"的地方做**。帧调度和分辨率缩放属于这一类；步数、法线、
> 包围体属于改变解的一类，动它们必须逐个验证，且不能和"保帧率"捆在一起上。

## 0.9.13 ⛔ 已回退 —— 提帧率尝试（见上）

**为什么之前卡**：`minFrame = 1000/24` 是个硬上限。24 fps 对 60 Hz 屏幕意味着**每一帧都踩不
同步的节奏**，看久了就是"卡卡的"——这跟 GPU 够不够快是两个问题。

但直接把上限改 60 会烧 GPU，因为真正的大头在 fragment shader：

```
每像素 ≈ 30 步 raymarch × 56 个 capsule
       + 命中后 4 次 map() 算法线（每次又是 56 capsule）
       + 触手再跑一次 armInfo（56 capsule）
≈ 最坏 2000 次 capsule / 像素
280×280 渲染 = 1.5 亿次 / 帧，24 fps 下 37 亿次 / 秒
```

所以三件事一起做：

### ① shader 砍成本

| 改动 | 效果 |
|---|---|
| `MAX_STEPS` 30 → **24** | 每像素 raymarch 上限降 20%（步长 0.985 本来就近理想，24 步够用） |
| 法线四面体 4 次 → **前向差分 3 次** | 复用已知命中距离，法线成本降 25% |
| `map()` 开头**双包围球早退** | 头顶球 r=1.15、触手团 r=2.4，球外的采样点**一个 capsule 都不算**直接返回距离 |

> 包围球半径是**故意放大**的：SDF 的界必须保守，给小球会让光线从触手之间穿过去。

### ② 去掉帧率上限

`minFrame` 直接删除，rAF 按显示器刷新率跑。

### ③ 自适应分辨率（游戏里的 dynamic resolution）

不牺牲帧率，改牺牲像素：

| 参数 | 值 |
|---|---|
| 初始 | 0.70 |
| 范围 | **0.45 ~ 0.85** |
| 掉帧（平均 > 20 ms） | 立即 ×0.88 降档（700 ms 冷却） |
| 满帧（< 17.3 ms） | 3 秒后 ×1.05 升档，且**不超过上次垮掉档位的 1.12×** |

最后一条是关键：降档时把 `scaleCeiling` 压到刚失败档位之上一点点，这样它**收敛**而不是在
"买不起的画质"和"买得起的画质"之间来回震荡。窗口尺寸变化时（换了成本模型）上限重置。

回调里只改 render target 大小，不动 CSS 尺寸——DOM 层的 400 px 不变，变的只是内部渲染精度。

## 0.9.12 触手改成欠阻尼弹簧（从"像"到"真"）

0.9.11 修掉抖动之后，触手虽然稳了，但**只会"黏"到目标姿态，不会甩**。原因：

```js
armPoints[i].lerp(armTargets[i], 1 - Math.exp(-(30 - point * 3.6) * dt))
```

一阶指数趋近 == **过阻尼弹簧（ζ = 1）**，而且不携带速度状态。数学上它只能单调逼近目标，
**永远不会越过目标再弹回来**。所以滑行时看不到"触手被水带着慢慢收拢、尖端回弹"。

改成带速度状态的二阶弹簧，半隐式积分（先速度后位置），每帧 2 个子步：

```js
const k = 800 - point * 100          // 根部 800 → 尖端 100
const zeta = 0.95 - point * 0.08     // 根部近临界 → 尖端欠阻尼 0.39
const c = 2 * Math.sqrt(k) * zeta
v += ((target - p) * k - v * c) * sub
p += v * sub
```

| 控制点 | 刚度 | ζ | 过冲 | t95 |
|---|---|---|---|---|
| 0（根） | 800 | 0.95 | **0%** | 0.21 s |
| 4（中段） | 400 | 0.63 | 2.8% | 0.13 s |
| 7（尖） | 100 | 0.39 | **24.5%** | 0.21 s |

**根部硬跟身体、尖端软且反弹** —— 这个梯度就是鞭子特性和拖曳感的来源。
过冲 24.5% 是刻意留的：没有过冲就没有"活物"感，过冲太大触手会自交。

### 为什么要 2 个子步

根部刚度 800 → ω_n ≈ 28.3 rad/s。ambient 模式 24 fps 时 `dt ≈ 41.7 ms`，
`ω·dt ≈ 1.18` 已经进入显式积分的失真区；拆成 2 个子步后 `ω·h ≈ 0.59`，稳定且相位准确。
实测在 `dt = 1/60 / 1/30 / 1/24 / 0.05` 四档下都不发散。

## 0.9.11 修掉"一移动就浑身抖"

**现象**：悬浮层一开始巡游，整只生物就高频抖动，不像在游泳；而且页面开得越久越明显。

**根因是相位写成了 `t × f(t)`**。触手行波原本这样算：

```js
Math.sin(t * (1.7 + swimPose * 2.4 + jetSurge * 0.7) + phase - i * 0.55)
```

`t` 是从打开页面起单调累加的时钟，而括号里的频率随 `swimAmount` / `jetSurge` 变。
微分一下，**瞬时角频率不是 `f(t)`，而是**：

```
d/dt [ t·f(t) ] = f(t) + t·f'(t)
```

第二项 `t·f'(t)` 随时间**无界增长**。实测（60fps 模拟）：页面开 10 s 后移动，相位速率已经
182 rad/s；2 分钟后 2078 rad/s；5 分钟后 **5182 rad/s**（约 825 周期/秒）——8 条触手 × 8 个
控制点全部按这个频率跳，根部刚度还是 30（时间常数 33 ms，等于瞬跟），于是整身一起抖。

**修法：相位只积分，不重算。**

```js
strokePhase += dt * (2.0 + swimPoseNow * 1.5 + jetSurge * 0.5)
const stroke = Math.sin(strokePhase + phase - i * 0.55) * (0.008 + i * 0.009) * (0.55 + swimPose * 2.2)
```

频率可以随用力程度轻微漂移，但**只要是累加的，瞬时速率就永远等于频率**。修复后三个时间点
（10 s / 2 min / 5 min）实测都是 3.68 rad/s 峰值、3.01 平均，**与 uptime 完全无关**。

> 这也符合真实章鱼：划水/喷水频率基本恒定（受生理上限约束），改变的是**幅度**和**时长**，
> 不是节奏。把频率从乘法里拿掉，既是修 bug，也是更真实的前提。

### 顺带：喷水从"线性衰减标志"改成非对称包络

原来 `jetSurge = Math.max(0, jetSurge - dt * 0.6)` —— 线性衰减，且是从 1 突跳开始的，
读起来像"一个数值在动"，不像"动物蹬了一下"。

现在每次喷水是一个**事件**（`jetPhase` 0→1，时长 0.85–1.15 s），包络：

| 阶段 | 时长占比 | 形状 |
|---|---|---|
| 收缩（主动） | 前 **22%** | `sin(p/0.22 · π/2)` — 快 |
| 舒张（被动） | 后 **78%** | `cos(…)^1.6` — 慢，尾巴拖长 |

**收缩快、舒张慢**这个不对称，是"活物感"的主要来源；匀速正弦恰好把它抹平了。

回归口径：三个 uptime 的相位速率必须一致；喷水包络必须能看出快升慢降，而不是对称钟形。

## 0.9.10 更自然的游动

- **修正身体俯仰方向**：之前身体的上下倾斜和移动方向是反的；现在头会朝着实际移动方向，转弯时带一点侧倾。
- **朝向改为阻尼跟随**：不再直接贴着瞬时速度，突然转向时有一点惯性，不会瞬间“甩头”。
- **喷水加入慢衰减的 `jetSurge`**：先加速、再滑行，而不是喷完立刻回到匀速；游得越快，喷水间隔越短。
- **触手逐点滞后**：根部跟身体紧，尖端跟得慢；高速时收拢、下垂、向后拖，不再被整体拽成一条斜线。

## 0.9.9 真实游泳姿态

- 参考真实章鱼：主要靠**喷水推进**（mantle 收缩、siphon 喷水），游泳时头在前、**触手向后拖成流线**；不是鱼鳍式划水。
- 提高划水/拖尾幅度：触手在移动时收拢、向后拖，尖端位移更大；喷水瞬间拖尾加强。
- 悬浮层移动速度会随喷水脉冲**加速/滑行**，形成 burst-glide，而不是匀速平移。
- 保留部分物种的“触手张开滑翔”作为慢速姿态。

## 0.9.8 游泳动作

- 悬浮层的移动速度/方向会实时传给生物：它会被移动方向带着**侧倾/俯仰**。
- 触手加入游泳 stroke：沿整条曲线传播的行波，移动时幅度更大；尖端会向运动反方向**拖尾**。

## 实现要点

- **three.js 打包进 `client.js`**（约 490 KiB min），React 保持 `require('react')` 外置。
- **透明合成**：renderer `alpha: true` + 场景不铺背景 + CSS `mix-blend-mode: screen`。深色身体在屏幕上几乎不增光，只有高光、眼睛、触手和 bloom 可见，所以不会出现一个黑色方框。
- **程序化 SDF**：整只生物是一个 signed distance field；每帧由 CPU 计算 8 条触手 × 8 个 Bezier 控制点，shader 里用 56 个 tapered capsule 与平滑并集融合身体和蹼膜，眼睛也参与同一 SDF 场；没有任何 GLTF/GLB（插件资源路由只允许图片）。
- **性能**：DPR 感知的自适应分辨率（设备像素 0.9–1.6，最低 360 px，不再是 CSS 0.45）、帧率跟显示器走、页面隐藏暂停、`prefers-reduced-motion` 降速、WebGL 失败静默降级；没有窗口可收起，卸载即 dispose。
- **升级安全**：通过 `shell.overlay` 注册组件，但把 fixed 层挂到 `document.body`，不覆写宿主类名。

## 已知限制与下一步

- 游走状态会持久化（`behavior-v1`），刷新后接着走；但不能拖拽，也不能被指针“叫住”，下一步可以加拖拽 + 好奇/跟随。
